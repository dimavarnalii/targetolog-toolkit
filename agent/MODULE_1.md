# Модуль 1: Дашборд для всіх клієнтів

> Для ШІ-агента. Спершу прочитай `SECURITY.md` і `agent/RULES.md`.

**Результат:** Дашборд у Claude по всіх кабінетах, лише читання  
**Потрібно:** Business Manager, токен ads_read, Claude з артефактами  
**Статус:** Збирач перевірено на підставних відповідях Meta, сторінка на вигаданих даних. На реальному кабінеті не пробував: перевірте на одному.

## GOAL
- Зібрати дашборд-артефакт у Claude (тип Dashboard) по клієнтських кабінетах Meta Ads. Лише читання, нічого не публікувати назовні.

## STATUS
- Готові: 1-dashboard/fetch_facts.py і page.html. Перевірено лише на вигаданих даних. Спершу ОДИН кабінет, потім решта.

## ASK_USER (по одному)
- Скільки кабінетів; для кожного: назва проєкту, ID (act_...), тип результату (lead, purchase, message), цільова ціна результату, для покупок цільовий ROAS. Валюта й часовий пояс кабінетів.

## USER_DOES_THEMSELVES (ти токена не бачиш)
- 1) developers.facebook.com: Create App, use case Marketing API, тип Business, прив'язати до свого Business Manager.
- 2) Business Settings, Users, System users: створити reporting-bot (роль Employee). Додати йому додаток.
- 3) System user, Add assets, Ad accounts: кожен кабінет з правом лише View performance.
- 4) Generate new token: свій додаток, право лише ads_read, Never expires. Токен показується один раз.
- 5) Токен задати змінною середовища META_TOKEN у своєму терміналі. Ти підказуєш текстом і значення не просиш.

## BUILD 1: збір даних
- config.example.json скопіюй у config.json і заповни з відповідей. Перевір логіку: python 1-dashboard/fetch_facts.py --self-test.
- config.json і out/ тримай поза папкою набору. Перший запуск на одному кабінеті: python -I <TOOLKIT>/1-dashboard/fetch_facts.py --config config.json --only "Назва" --days 30 --out out. Порівняй spend за вчора з Ads Manager. Дашборд у USD: для іншої валюти скрипт попередить.
- Якщо результат не той, що вважає користувач, задай result_action у config.json (наприклад onsite_conversion.lead_grouped; для message дефолт не перевірений). Лише потім додавай решту кабінетів.
- META_TOKEN має бачити й заплановане завдання: постійна змінна середовища (Windows: setx), перезапуск застосунку. Значення в чат не просити.

## BUILD 2: артефакт
- Artifact quickstart (intent other): створи з типу Dashboard, прочитай його настанови до кінця.
- Набори даних (id важливі): facts, projects, clients як file (json) з файлів out/; report_items як file, порожній масив. Сторінка: 1-dashboard/page.html стає files/index.html.
- Перевір інструментами типу (check, runs, page): набори без помилок, на сторінці цифри. Артефакт приватний.

## BUILD 3: оновлення й звіти
- Заплановане завдання щодня зранку: fetch_facts.py --days 60 і повна заміна файлів наборів (ідемпотентно, без дублів).
- Заплановані завдання звітів: день щодня 11:45 і тиждень щопонеділка 12:00 за Києвом (так написано на сторінці). Читають facts, застосовують STATUS_RULES і замінюють файл report_items: рядки {report: daily|weekly, kind: headline|verdict|scale|watch|pause, order (число), project (точна назва), ad (жирний заголовок), text, metric}. headline і verdict по одному на звіт; зелений стан лише якщо verdict.text дорівнює "Усе в нормі".
- Пропущений день не надолужується: нагадай дивитись журнал раз на тиждень.

## STATUS_RULES (пороги задані константами в page.html: зміниш їх там)
- Працюють за період від 7 днів і ціною результату (CPR).
- Вигорає: CPR за останні 3 дні гірша за CPR періоду більш ніж на 1/3, або є витрати без результатів.
- Росте / Погіршується: CPR змінилась на 15% і більше проти такого ж попереднього періоду.
- Без результату: від $30 витрат і 0 результатів. Мало даних: менше $20 витрат. Новий: у попередньому періоді майже без витрат.

## KNOWN_LIMITS
- Meta міняла вікна атрибуції в Insights API (7d_view і 28d_view прибрані, за даними на 2026-01-12): звір з поточною документацією.
- До 90 днів за запуск; сьогодні неповний, звіти беруть вчора. LTV і MRR у Meta немає: monthly_fee, monthly_budget задає користувач; status має бути active.
